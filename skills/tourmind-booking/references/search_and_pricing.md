# Hotel search and price comparison

<a id="inputs"></a>
## Inputs, budget and currency

- Before searching, establish the location, check-in and check-out. Infer unambiguous details and state any assumptions with the results. Resolve relative dates in the user's timezone; for a missing year use the next future occurrence. Send `YYYY-MM-DD` with check-out after check-in.
- Default to one room and one adult per room when unspecified. State the assumed occupancy and invite corrections. Default to zero children and `children_ages=[]`. Preserve any counts already supplied. `adults`, `children` and the children's ages describe **one room**, repeated `room_count` times. Require one age (0–17) per child in each repeated room configuration. If only totals for several rooms are supplied, ask for the per-room split. Mixed configurations and `room_occupancies` are unsupported.
- Treat dates, occupancy, room count, explicit radius, strict budget, required star rating, facilities and property type as hard constraints. Distinguish preferences such as closer, cheaper, higher star rating, breakfast, free cancellation or a preferred room type. Do not widen the user's constraints without consent.
- Unless explicitly a trip total, interpret a hotel budget range such as “300–400” as **per room per night** and state that assumption. Multiply by nights and rooms once to compare stay totals. Do not multiply an explicit trip total again.
- Signed in, use after-coupon room charges for budget and price sorting by default. Omit both `lowest_price` and `highest_price` from `search_hotels`: its pre-coupon filters could discard a match. Apply both requested bounds locally to comparable prices after checking coupons. When signed out, when coupons are declined, or for an explicit pre-coupon budget, the original price filter applies. Any bound sent to the API must be a **CNY total for all rooms and nights**. Convert each supplied bound at a current live rate if necessary. If the required conversion is unavailable, ask for a CNY budget or offer an unfiltered search with the user's agreement.
- Display hotel and room prices in CNY for Chinese requests, USD for other languages, or the user's explicitly requested currency. Compare on the same stay and currency basis. For display conversion use a current live rate for both nightly and total amounts, mark them approximate, and give the rate, source and retrieval time. Keep the original transaction currency and amounts for verification and booking. Use TourMind data for hotels, coordinates, images, rates, inventory and policies.

<a id="location"></a>
## Resolve the location

| Request | Route |
|---|---|
| City, district, neighborhood, business area, large attraction, park, resort, ski area or island | Use the active channel's `search_location`; inspect `data.regions[]` before `data.place` unless the user gives an exact point or radius. Match the full destination phrase to the name or full name (including the Chinese variants), check country/city and `region_type`. A positive `hotel_count` supports a match but is insufficient alone. Reject unrelated namesakes. Ask one focused question if several matches remain plausible. Pass the selected string `region_id` and resolved `location_name` to `search_hotels`; preserve the returned area names and distances. |
| Exact hotel name | Resolve the hotel and coordinates through keyword-mode `search_hotels`; use `get_hotel_detail` for static details and `query_room_rates` for live prices. |
| Station, address, entrance, compact landmark, map pin, explicit radius or distance from an exact point | Send the full POI phrase and destination context to `search_location`. It returns one Google Places result: use `data.place` only if name, address and city/country match. Send `place.latitude`, `place.longitude`, `radius_km` and `location_name=place.name` to `search_hotels`. Keep the exact requested radius. Otherwise use `place.recommended_radius_km` (currently 3 km for “nearby”). State the returned `search_scope`. |
| Broad POI with no reliable region | A matching place is a representative point. If no radius was specified, start at the recommended radius, then try the next larger values from 3, 5, 10, 20 km as needed. Stop at five candidates, a response hitting the 20-hotel limit, or 20 km. Merge by string `hotel_id`, retaining narrower-radius candidates and distances. Disclose the final scope and reason for expansion. If fewer than five remain at 20 km, ask which entrance, visitor center or gateway town is preferred, or offer a wider disclosed search. Do not silently jump to 50 km. |

If neither a region nor a place matches, report that the location could not be resolved. Never invent coordinates, use a hotel or city center as a substitute for the requested point, or describe a city-wide search as nearby.

<a id="compare"></a>
## Verify, compare and present

1. Preserve the original candidate pool, identifiers and distances. Region/nearby searches return up to 20 live-probed candidates; keyword mode does not perform that probe. In every mode `min_price` is cached. Record known hard-condition failures and keep them available for “show all”; defer coupon-inclusive budgets until coupon prices are known.
2. For one hotel, use `query_room_rates`. For multiple hotels, use `batch_query_room_rates` across the pool needed for fair comparison, at most 20 IDs per batch and three concurrent batch requests. The server controls workers inside each batch. Read each result independently; do not replace missing, empty or failed batch items with individual calls. Preserve successful items and each hotel's own result-page URL.
3. Match products to dates, rooms, occupancy, meal and other requirements. Adult and child capacity are separate per room; absent child capacity is unknown. Use the documented [capacity](parameter_guide.md#adult-and-child-capacity) and [meal mapping](parameter_guide.md#meal-type-mapping). Verify required or preferred facilities via `get_hotel_detail` when needed. Only `rate.is_on_request=false` proves immediate bookability. A request product requires supplier confirmation: exclude it when immediate availability is required, otherwise label it and rank it after immediately bookable options.
4. Establish the price for **each otherwise matching quote needed for ranking or display**, before applying price limits, price sorting or selecting hotels/rooms:
   - **Signed out:** skip coupon lookup and show the original live price. With the first priced result, once per search, show this invitation in the response language: “Register or sign in to see available coupons. You may get a lower price.” Continue through room selection, availability and the full booking review without blocking on login.
   - **Signed in:** unless coupons were declined, automatically call `check_room_availability` and then [`query_available_coupons`](parameter_guide.md#query_available_coupons) for that exact quote under the same account and channel. Use the latest checked rate, hotel, stay dates, transaction currency and **pre-coupon total for all rooms and nights** from the verified occupancy. Use the selected `rateInfos[].currencyCode`; match any returned coupon currency to it. A mismatch requires fresh verification. Do not reuse another product's, account's or channel's coupon.
   - **Coupons declined:** for a hotel or room list, compare the matching original prices from `query_room_rates` or `batch_query_room_rates`. For immediate availability, filter these products to `rate.is_on_request=false`. Skip coupon lookup and per-product availability checks at this stage. Verify the product under the current identity when selected for final review or when the user explicitly requests verification.
   - **Coupon results:** compare the lowest returned `payable_amount` for this product; identify the coupon and mark the total “After coupon”. A discounted nightly figure is the average per room per night. For a successful empty list, use the checked live price without a coupon label. If the user asked about discounts for that quote, explicitly tell them that no coupons are currently available for it. An explicit pre-coupon budget still uses the original price for filtering; make that basis clear even when also showing a discount.
   - Preview may issue an entitlement once per account/campaign configuration. It does not reserve quota or bind an order. Only Skill campaigns use the shared quota (configured total less reserved and redeemed uses); an ordinary coupon in the eligible list may have `remaining_quantity=0`. Do not exclude it or describe this field as the user's coupon count.
5. Apply explicit sorting first. Otherwise rank by verified preference match, immediate bookability, distance, comparable stay total, then cancellation flexibility. Show up to five qualifying hotels. Fetch each hotel's static detail, image, address, facilities and explicit mandatory-fee disclosures. Provide two or three specific verified match reasons, such as closest bookable hotel, lowest verified four-night total or a verified pool. Use the [hotel list](response_templates.md#hotel-list) and [room details](response_templates.md#room-detail). For a hotel selection, return its details, room images and up to five distinct matching room products with live rates in one response; offer the rest.
6. For “show all”, include the complete original pool, group matches and nonmatches, and list every failed hard constraint per nonmatch. Verify each additional hotel's live rate and fetch the required static details. If there is no matching live product, retain the hotel with “No matching live room or quote”. Never invent prices or pad a shortlist. State the actual scope verified.

<a id="copied-product"></a>
### Match a product copied from a results page

Parse the available hotel/address, dates, room, rooms, beds, meals, occupancy, nationality, prices and cancellation terms. Match the selection to the active channel's live room products. If several match, show the material differences and ask the user to choose. A copied price or inventory is provisional. Continue to [final verification](booking_and_payment.md#book) with the chosen product's live rate code. Refresh rates, availability and applicable coupons after sign-in or any change of account, channel or quote.

<a id="failure"></a>
## Empty results and failures

| Result | Action |
|---|---|
| No candidates, or fewer than five qualify | State the exact constraints and what limited the result. Offer changes to dates, occupancy, budget or radius without applying them. An empty pre-coupon budget search may be probed once without price bounds to diagnose over-budget inventory; identify those results separately. |
| Candidates but no matching products; `reason=no_matching_live_room` | This is a successful empty result. Say that hotels were found but no matching live rooms were returned; suggest other dates or occupancy. |
| `hotel_not_found` | Hotel missing or unavailable. |
| `upstream_timeout` | Pricing timed out; a later retry may succeed. |
| `upstream_error` / `hotel_detail_unavailable` | Report the service error or temporarily unavailable hotel details. Neither proves rooms are sold out. |
| `invalid_request` | Correct the request before retrying. This may also occur at the top level of a malformed single or batch request. |
| Authentication/authorization failure | Stop the affected authenticated operation and follow [access recovery](access_and_updates.md#auth-errors). For 401/`unauthorized`, invalidate the rejected credential at its recorded source and never silently try another token or channel. For ToB 403/`HOTEL_BUSINESS_PERMISSION_REQUIRED`, keep the valid token and direct the user to the account administrator or TourMind support. |
| Selected rate fails availability checking | Retry the same rate once only for a safely retryable transient failure. Report an unresolved error and exclude that quote from available or after-coupon results. |
| Ordinary coupon lookup fails for one quote | If the room price was verified, show it as “Before coupons; coupon check unavailable”. Keep it separate from verified coupon-price rankings and budget matches, and continue with other quotes. An error is not an empty eligible list. |

Apply rate-query reasons per single response or per `data.results[]` item, even when the batch succeeded. Retry other transient failures only when safe, then report the concrete error and stop the affected operation. Show only fields returned by the active channel. Never disclose a full token, raw secret, internal payment code or `rate_code`.
