# TourMind hotel booking

## Start here: identity, welcome and updates

1. **Resolve the channel at the start of each workflow.** Read `{baseDir}/skill_token.txt`; only if it is missing or empty may you check `{baseDir}/../flight-booking-ai/skill_token.txt`. Keep the credential's source path private. With neither token, browse public ToC without credentials. A `uk_` token selects personal ToC: send the current `user_key` on every `search_hotels` call and follow each other endpoint’s credential rules; `sk_` selects business ToB (`token` on every request). Stop on an unrecognized nonempty token; never look elsewhere for a replacement. For a token the user provides or a rejected credential, follow [credential handling](references/access_and_updates.md#credentials) or [401/403 recovery](references/access_and_updates.md#auth-errors).
2. **Once after installation, before the first hotel task:** show the [complete welcome message](references/response_templates.md#first-run) in the user's language, with all three examples. Use the authorization ending for the resolved credential. Do not repeat the welcome in later conversations.
3. **Before the first workflow API call in each new conversation, or on resuming after at least 24 hours of inactivity:** call `check_skill_update` with `current_version` from this file's `metadata.version`. For no token or `uk_`, POST to `/skill/toc/check_skill_update` with the version only; for `sk_`, POST to `/skill/tob/check_skill_update` with the token and version. If conversation state is unknown, treat this as first use. A failed check never blocks the task. Do not repeat the check per endpoint; handle a visible update using [update results and installation](references/access_and_updates.md#updates).
4. **With the first priced result of each signed-out search,** show this invitation once in the response language: “Register or sign in to see available coupons. You may get a lower price.” Skip coupon lookup and continue through public rates, availability and booking review. Use the [full sign-in guidance](references/response_templates.md#sign-in) when the user requests their coupons, proceeds to create an order or wants to manage one.

## Availability, booking and payment workflow

Start at the row matching the request. An existing order does not require dates, a new hotel search or a new coupon lookup.

| User wants to… | Next actions |
| --- | --- |
| Find or compare hotels | Resolve [dates, occupancy and budget](references/search_and_pricing.md#inputs) and [location or POI](references/search_and_pricing.md#location). Search candidates, fetch live room products, then [verify, filter and rank](references/search_and_pricing.md#compare). Show up to five qualifying hotels using the [hotel list](references/response_templates.md#hotel-list). |
| See one hotel or its rooms | For an identified hotel, fetch both its details and its live room rates on the active channel, without a new discovery search. For price comparisons use the same [quote and coupon rules](references/search_and_pricing.md#compare). Render the [hotel and room details](references/response_templates.md#room-detail). |
| Check their coupons | If signed out, show the [sign-in guidance](references/response_templates.md#sign-in). For the active account and channel, verify the selected live quote if needed, then [look up its eligible coupons](references/parameter_guide.md#query_available_coupons). If the lookup succeeds with `coupons=[]`, tell the user in the response language: “No coupons are currently available for this quote.” For a failed lookup follow [error handling](references/search_and_pricing.md#failure). |
| Book a selected room | Follow [final verification and creation](references/booking_and_payment.md#book): check the selected rate, refresh eligible coupons if signed in and coupons were not declined, and present the [complete booking review](references/response_templates.md#booking-review). Signed-out users may confirm the public price before signing in. Before creating, require a matching credential, explicit confirmation, the guest's legal name and a valid contact email. Return the order reference and check its status. If `UNPAID`, offer the [supported payment methods](references/booking_and_payment.md#payment) and wait for the user's choice. If creation is inconclusive, follow [request-ID recovery](references/booking_and_payment.md#recovery) before another attempt. |
| Check, pay or cancel an order | Use the creation channel and its matching credential. [Look up the order](references/booking_and_payment.md#order) by reference. For [payment](references/booking_and_payment.md#payment), use the order currency to offer supported methods; obtain method confirmation, including the [fee and refund review](references/response_templates.md#payment-review) for Stripe. For [cancellation](references/booking_and_payment.md#cancel), verify the order, disclose the relevant refund terms and obtain explicit cancellation confirmation. An inquiry alone authorizes neither action. |

**When comparing prices:** for a signed-in user who has not declined coupons, fetch the live rate, run `check_room_availability`, then `query_available_coupons` for each otherwise qualifying quote needed for comparison **before** coupon-based filtering, ranking or display. Signed-out comparisons use original live prices. When the user declines coupons, list matching live rate products at their original prices and run `check_room_availability` only for a selected product or a quote the user explicitly asks to verify. An explicitly pre-coupon budget always filters on the original price. A failed lookup is not an empty coupon list.

**When identity or terms change:** [refresh the rates and availability](references/access_and_updates.md#switch-channel), refresh applicable coupons and show any changes. Never carry a rate or payment context across channels. Reconfirm a switch between signed-in accounts or channels, a replacement of a confirmed coupon quote, or a change to the selected coupon, price or other booking terms. A guest signing in to personal ToC can retain the public-price confirmation if the terms are unchanged.

## Evidence, language and API contracts

- Use TourMind responses for hotel facts, photos, policies, inventory and rates. A cached `min_price` cannot establish a live price. Only a matching live product with `rate.is_on_request=false` may be described as immediately bookable. Do not relax hard constraints silently.
- Reply in the language of the request unless the user asks otherwise. Translate user-visible text while preserving facts, variables, Markdown and API values. For returned result links, [change only the supported locale segment](references/parameter_guide.md#returned-result-page-url-language); never reconstruct the URL or its access ticket.
- Before constructing a request or interpreting its fields, read the relevant endpoint in the [API and field reference](references/parameter_guide.md). For empty or failed searches use [search recovery](references/search_and_pricing.md#failure); for an uncertain booking use [creation recovery](references/booking_and_payment.md#recovery). Report persistent API errors truthfully in the user's language, quoting the raw error unchanged except for secrets. Never expose complete tokens, internal payment codes or rate codes.
